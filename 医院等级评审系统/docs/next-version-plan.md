# 医院等级评审系统 v0.2 开发计划（生产导向、本地数据版）

> 版本定位：开发和验收仍在本地，继续使用虚构医院、合成数据和本机服务；但功能、数据模型、权限、安全、接口和运维按未来真实医院落地的方向设计。当前不连接真实医院、不接入真实患者数据、不发布公网。
>
> 本计划基于当前 v0.1 演示、工作区原始资料、`fitness-feature-hh` 的本地项目与 GitHub 代码审阅，以及国家卫生健康委公开的 2025 年版三级医院评审标准。原始 `docs/01` 至 `05`、政策文件和参考 PDF 不修改；新增口径只写在本文件及其配套开发文档中。

## 1. 目标

v0.1 已能走通“指标监测 → 数据核查 → 前置自评 → 试算 → 改进 → 报告”的单医院演示链路。v0.2 的目标是建立可替换真实数据源的**生产导向评审平台骨架**：标准有版本，条款能分派，数据可追溯，材料有版本，问题能闭环，结论能解释，用户和医院范围由真正的认证与授权控制。合成数据只负责填充输入适配器，不进入核心业务规则。

本版本不在缺少真实数据时伪造 203 条指标的生产结果，而是先建立能承载完整标准的规范化结构、导入校验和接口边界，并用覆盖五个章节的 40 条左右代表性指标证明设计可扩展。界面必须明确标记“演示口径”和“合成数据”；代码必须同时提供未来接入真实数据、对象存储、统一身份和消息服务的适配接口。

## 1.1 生产导向原则

1. **核心业务不依赖演示实现**：合成数据、H2 文件库、演示角色头和本地文件目录只能位于 profile/adapter 层；条款、任务、材料、指标、审计和报告使用稳定领域接口。
2. **默认安全而不是默认方便**：真实部署配置必须关闭演示角色切换、禁止匿名访问、启用强认证、最小权限、租户/医院/科室范围校验和敏感数据脱敏。演示模式显式标记为 `demo`，不能通过改请求头伪造生产身份。
3. **数据可追溯和可重放**：所有指标结果都能追溯到来源批次、口径版本、计算规则、执行时间和操作者；批次失败不污染已发布快照。
4. **不可变与可审计**：标准发布版本、评审快照、材料版本、审计记录和结论不能被覆盖删除；更正通过新版本或冲正记录完成。
5. **真实部署能力分阶段完成**：本版先实现生产形态的接口、配置和测试替身，待用户提供真实数据字典、身份方式、网络和部署条件后，再做联调、渗透测试、性能容量和上线验收。

## 2. 外部依据与可借鉴结论

### 2.1 规范口径

- 国家卫生健康委已发布《三级医院评审标准（2025 年版）》，并废止 2022 年版及其实施细则。新版强调功能定位、医疗服务能力、质量安全、专科建设和线上/日常监测。[通知](https://www.nhc.gov.cn/yzygj/c100068/202506/25229edc80d34694b7debf54ddef9f9f.shtml)
- 公开标准摘要显示新版包含 203 条日常监测指标，评审周期为 4 年，周期内违反前置要求可延期一年，并明确不得使用或变相使用“千分制”等过度形式化方式。[标准 PDF](https://www.nhc.gov.cn/yzygj/c100068/202506/25229edc80d34694b7debf54ddef9f9f/files/%E3%80%8A%E4%B8%89%E7%BA%A7%E5%8C%BB%E9%99%A2%E8%AF%84%E5%AE%A1%E6%A0%87%E5%87%86%EF%BC%882025%E5%B9%B4%E7%89%88%EF%BC%89%E3%80%8B-20250610154952298.pdf)
- 国家卫健委政策解读明确提出更加重视信息化手段、线上评审和日常数据监测，弱化脱离实际的形式化打分。[政策解读](https://www.nhc.gov.cn/yzygj/c100067/202506/0795d62eece44307915d639486263a39.shtml)
- 评审办法要求提交评审周期内的自评、检查整改、年度病案首页及其他质量安全、效率和诊疗水平数据，因此系统要保存“周期—年度—月度—来源—快照”的关系，而不是只保存一个最终分数。[医院评审暂行办法](https://www.nhc.gov.cn/wjw/gfxwj/201109/55bd504b1905407ba1b6aefe772d14b4.shtml)

### 2.2 FitChain 项目的可迁移做法

本地 `fitness-feature-hh`（GitHub: [cjc403/Fitness](https://github.com/cjc403/Fitness)）中值得迁移的是工程方法，不是健身房业务：

1. **模块边界**：按 `module/xxx/{entity,repository,dto,service,controller}` 拆分业务，避免当前 `DemoService` 和 `SyntheticData` 继续膨胀。
2. **权限单一事实来源**：后端 `RolePermissionCatalog` 负责真正授权，前端只负责菜单和路由展示；医院系统对应建立 `ReviewRolePolicy`，所有写接口继续做服务端范围校验。
3. **追加式变更**：FitChain 的 Flyway 迁移只增不改；演示版虽然暂不换 PostgreSQL，也应给 H2 快照增加 `schemaVersion`、显式迁移器和向后兼容测试。
4. **真实回执和幂等**：写入前冻结请求、写入后回查状态、重复请求返回原回执。评审系统的补录、材料上传、任务状态变更和报告生成都采用同样模式。
5. **隔离验收**：真实浏览器验收只写隔离数据，测试报告区分“执行通过”和“跳过”，保留复现证据，不用 UI 隐藏代替权限安全。
6. **交接文档和计划先行**：每个功能都有范围、接口、测试门槛和回滚边界，适合多个 AI 共同维护。

### 2.3 其他公开系统的借鉴边界

- [nikhilgupta-9/hospital-quality-management](https://github.com/nikhilgupta-9/hospital-quality-management) 展示了 NABH 合规门户的基础拆分：标准/文档面板、HR、设备与基础服务、四类角色、部门范围过滤和按领域迁移。可借鉴其**领域分组与部门范围**，不能把其 foundation 阶段的占位页面当作完整评审实现。
- [hmislk/hmis](https://github.com/hmislk/hmis) 是长期演进的开放医院信息管理系统，说明评审工具未来应通过标准接口消费 HIS/EMR/LIS/PACS 等数据；当前演示只做合成数据适配层，不直接复制其临床业务。
- [WAD-Team-Alpha/Hospital_Review_System](https://github.com/WAD-Team-Alpha/Hospital_Review_System) 更接近医生/医院展示、预约和评价网站，不是医院等级评审系统。它可参考资料导航和角色首页，但不采用其“医院评分/评论”作为等级评审判定逻辑。
- 商业评审产品普遍强调“标准查阅、条款分配、多次自评、文档管理、PDCA、自动报告”。这与本项目的下一步方向一致，但商业宣传不作为政策依据；实现时以国家标准和本工作区政策为准。[产品示例](https://www.qcc123.cn/product-detail/BvXr589W)

## 4. v0.2 交付范围

### 4.1 标准与条款中心（P0）

- 新增标准包元数据：`standardId`、版本、来源、发布日、生效日、适用范围、状态（draft/published/retired）。
- 条款树支持章节、条款、指标、前置要求四级关系；每个条款保存要求说明、证据类型、责任范围、评价方式、来源定位。
- 支持导入演示 CSV/JSON 标准包，导入前做编码、重复 ID、缺父节点、缺单位、阈值方向校验；发布后只读，修订生成新版本。
- 预置 2025 版五个章节名称和代表性指标；明确“演示覆盖集”，不声称完整 203 条。

### 4.2 任务与协同（P0）

- 条款批量分配给部门、岗位和具体负责人，支持截止日期、优先级、依赖项和提醒状态。
- 任务状态：`todo → in_progress → submitted → returned → accepted → overdue → cancelled`；所有状态变更记录审计。
- 任务提交可同时关联指标填报、制度文件、会议纪要、整改记录或现场照片；退回必须有原因。
- 领导首页展示章节完成率、逾期率、证据完整率和红灯条款；科室只能看本部门范围。

### 4.3 证据资料库（P0）

- 佐证对象统一为 `EvidenceItem`，通过关联表挂到条款、任务、指标、前置或整改单。
- 每次上传生成版本、SHA-256、上传人、上传时间、材料类型、有效期、审核状态；旧版本保留只读。
- 支持按条款、科室、材料类型、状态检索；下载按角色校验，患者级内容继续禁止进入领导和信息角色。
- 增加材料清单视图和“缺证据/已过期/待审核”筛选。

### 4.4 数据采集与质量链（P0）

- 将当前指标事实抽象为 `DataSource → CollectionBatch → MetricFact → CalculationTrace`。
- 演示先提供三种适配器：合成数据、人工填报、CSV 导入；不接真实 HIS/EMR/LIS/PACS。
- 每个结果保存口径版本、输入范围、分子/分母、排除数、计算时间、质量警告和批次 ID；相同批次可重放。
- 质量规则覆盖缺失、重复、单位错误、分子大于分母、期间重叠、部门无归属、异常跳变；错误批次不进入试算。

### 4.5 周期自评与试算（P0）

- 评审周期采用 4 年模型：周期起止、年度节点、月度采集、周期内重点检查、整改复核。
- 试算输出章节级和指标级结果，不使用“千分制”作为主界面；保留符合/不符合/不适用/证据不足/延期等状态。
- 前置要求与监测指标分开计算；违反前置或真实性抽查超阈值时，明确显示延期原因、触发条款、所需整改动作。
- 每次试算保存不可变快照，报告只引用快照；支持两次试算差异对比，标出新增、恢复、恶化和口径变更。

### 4.6 整改闭环（P0）

- 由条款、指标、抽查或外部检查事件创建问题；自动带出责任部门、风险等级、根因、措施、截止日期和验证方式。
- 保留现有改进单状态机，增加问题来源、复核人、效果指标、前后证据和逾期升级；关闭前必须有复核结论。
- 复核结论支持 `improved / partially_improved / not_recovered / invalidated`，不得只靠填写状态关闭。

### 4.7 角色与审计（P0）

- 建立 `ReviewRolePolicy`，至少覆盖评审办、院领导、科室负责人、指标管理员、材料管理员、观察员。
- 服务端强制医院/科室/条款范围；前端隐藏菜单只作为体验优化。任何导出、下载、成员下钻、状态变更都入审计。
- 审计记录支持按人、动作、对象、时间和请求关联 ID 查询；敏感字段只保存脱敏摘要。

### 4.8 生产形态基础设施（P0）

- 持久化层提供 PostgreSQL 实现，保留 H2 仅作为本地测试实现；核心领域不得直接依赖 H2 特有 SQL 或 JSON 快照结构。
- 附件提供本地目录、S3 兼容对象存储两个实现，元数据和内容分离；下载使用短时签名或后端流式授权，禁止把真实文件路径暴露给前端。
- 认证提供本地测试账号、OIDC、LDAP/AD 的接口边界；生产 profile 禁止 `X-Demo-Role`，登录、退出、会话撤销、MFA 扩展点和密码策略由认证层负责。
- 以医院为租户边界，科室、岗位、用户和条款责任范围由服务端强制过滤；所有列表、导出、批处理和异步任务都带租户上下文。
- 增加结构化日志、请求关联 ID、健康检查、指标端点、失败告警接口、定时备份和恢复演练脚本；本地只使用无外发的日志和监控替身。

### 4.9 数据集成与脱敏（P1）

- 建立 HIS/EMR/LIS/PACS/病案首页等外部系统的只读适配器契约：连接配置、字段映射、编码字典、增量游标、重试、死信和批次回执。
- 首先实现 CSV/JSON 和合成适配器；真实接口只做契约测试与模拟服务器，不填入真实地址、账号或患者数据。
- 统一患者/病案/科室等敏感标识的内部引用和脱敏投影；领导、观察员和导出文件默认不含患者级字段。
- 数据质量问题进入可追踪队列，支持人工纠正、重新采集和批次重放，不能直接编辑最终指标值。

### 4.10 前端评审工作台（P1）

- 首页改为四块：周期进度、待办与逾期、短板雷达、证据缺口。
- 条款中心提供树状导航、筛选、责任人、完成状态、证据数、最新数据批次和差异入口。
- 任务、证据、指标、整改使用统一抽屉/详情页，减少重复跳转；移动窄屏先保证只读和审批，不承诺真机验收。
- 报告中心支持试算快照选择、章节预览、DOCX 导出和“本报告使用的证据/数据批次”清单。

## 5. 技术实施顺序

### 阶段 A：生产边界与契约（第 1 周）

1. 先新增 `docs/next-api-contract.md`，定义标准、条款、任务、材料、批次、质量报告、周期、比较、认证上下文和错误码接口。
2. 先定义领域模型、租户上下文、审计事件、文件存储接口、认证接口和外部数据适配器接口，再接合成实现。
3. 重构 `SyntheticData` 的平行数组为 `IndicatorDefinition` 列表；重构 `DemoService` 为 `StandardService`、`TaskService`、`EvidenceService`、`ScoreService`、`AuditService` 的薄协调层。
4. 给状态快照增加 `schemaVersion` 和迁移器；写旧 v0.1 快照升级测试，不能用 reset 代替迁移。
5. 增加 PostgreSQL schema/migration 草案和 H2 契约测试；本地不要求启动生产数据库，但领域测试必须不依赖 H2 专有行为。

### 阶段 B：标准、任务、材料（第 2–3 周）

1. 实现标准包导入/校验/发布和条款任务分配。
2. 实现证据版本、关联、审核和权限下载。
3. 先完成后端领域测试，再接前端；接口变更先更新契约文件。

### 阶段 C：数据质量与周期试算（第 4–5 周）

1. 实现批次、事实、计算链和质量报告；补充 CSV 导入的失败样例。
2. 实现 4 年周期、试算快照、对比和延期原因解释。
3. 更新 DOCX 报告，把来源批次、证据缺口和口径版本写入报告。

### 阶段 D：工作台与闭环验收（第 6 周）

1. 完成条款中心、任务台、证据库、周期总览和报告中心。
2. 按五条演示路线做浏览器验收：标准导入→任务分配→证据上传→数据质量错误→整改复核→报告下载。
3. 重跑现有基线，再补 v0.2 新增检查；最终重置为干净初始演示状态。

### 阶段 E：上线前工程能力预留（第 7 周，可与 D 并行）

1. 完成 PostgreSQL、对象存储、OIDC/LDAP、外部数据源的配置样例和本地替身；密钥只从环境变量或受保护配置读取。
2. 增加迁移校验、备份/恢复、审计留存、日志脱敏、权限越权、文件上传和依赖漏洞检查。
3. 建立性能基准：条款树、任务列表、证据检索、指标批次和报告生成的分页、索引与超时边界；记录基线，不虚构生产 SLA。
4. 产出《真实接入清单》：需要用户提供的数据字典、接口样例、身份协议、组织架构、保留期限、部署网络和验收账号。

## 7. 验收标准

### 功能验收

- 能导入并发布一个演示标准版本，显示五章节和指标/前置关系。
- 能把条款分派到科室，科室提交任务和材料，质控退回并重新提交。
- 同一材料至少有两个版本，旧版本可查但不能覆盖新版本；领导、科室、观察员看到的范围不同。
- 能导入一个故意有质量错误的 CSV，系统阻断该批次进入试算并给出可定位的错误行/规则。
- 能在 4 年周期内生成两次试算，比较差异，触发前置延期并在报告中解释。
- 能从红灯指标或抽查问题创建整改单，提交证据、复核效果并保留全链路审计。

### 工程验收

- 现有后端 27、前端 18、服务 3、集成 7 组检查不回退；未运行的检查继续标注“未验证”。
- 新增后端测试覆盖标准导入、任务状态、材料版本、质量阻断、周期快照、角色范围和幂等；新增前端测试覆盖条款筛选、批量任务、证据版本和对比视图。
- 真实浏览器完成至少一条从条款到报告的流程；报告 ZIP/XML 有效，且基于同一快照重下载字节稳定。
- Java/Node 进程启停和根目录启动器回归通过；依赖目录、构建结果、运行库、日志和测试上传文件不进入版本库。
- 生产 profile 的自动化检查确认：演示角色头被拒绝、未认证请求被拒绝、跨医院/跨科室读写被拒绝、文件路径不可探测、审计事件完整；本地 demo profile 只作为测试替身。
- PostgreSQL migration 可在空库和升级库执行；备份文件可恢复到隔离库；对象存储和认证替身能在无真实凭据情况下完成契约测试。

## 8. 当前暂不启用，但必须预留生产接口

- 不在 v0.2 连接真实 HIS、EMR、LIS、PACS、DRG 或国家平台；先建立适配器边界、字段映射、批次回执和模拟服务器。
- 不在本轮启用真实统一认证、生产等保、患者隐私治理、公网发布或真实医院上线；但要先实现认证、租户、审计、存储、备份和监控的生产形态接口及本地替身。
- 不把商业产品宣传内容、GitHub 业余项目或本地合成数据当作政策依据。
- 不为了“203 条”而复制不清晰的原文；完整标准导入必须有来源定位、版本和人工复核记录。
- 不优先开发开放式 AI 自动填报。若后续加入 AI，只允许检索/解释/生成待办草稿，写入仍需人工确认、权限校验和回查。

本版本完成后仍不能直接称为“可上线生产系统”。真实落地前还必须完成真实数据字典和接口联调、身份与组织目录接入、等保/安全评估、性能容量、灾备、隐私影响评估、现场业务验收和上线回滚演练。
