# 医院等级评审系统 v3 开发计划（WorkBuddy 执行版）

> 文档状态：开发指令与验收基线，尚未开始实现。执行负责人：WorkBuddy。当前版本仍只允许在本地使用虚构医院、合成数据和本地服务；本计划把产品能力向未来真实医院落地方向推进，但不连接真实医院、不接触真实患者数据、不发布公网。

## 1. 版本定位

v3 定位为**生产接入验证版：数据中台与指标引擎**。

导师提供的两份产品参考材料把方向指向四个能力：标准指标库、多源数据接入与清洗、持续监测与指标下钻、预警和 PDCA 整改闭环：

- `C:\Users\CJC\Desktop\医院等级评审系统开发\医院等级评审管理系统.pdf`：强调 2025 版标准、全院数据中心、多源业务系统接入、指标自动计算、AI/规则预警、PDCA 和自评报告。
- `C:\Users\CJC\Desktop\医院等级评审系统开发\01.医院等级评审系统v2.pdf`：强调标准指标库、医疗质量数据中台、ETL 清洗编码、持续监测、科室/人员/患者明细下钻、权限配置和人工/Excel 补录。

两份材料是产品与研究方向参考。当前标准口径仍以工作区正式政策、标准包和契约为准；PDF 中基于 2022 版或商业产品的数量与宣传性结论不得直接写入评分规则。

v3 不以“复制全部 203/232/364 项指标”为第一目标，而以一条可重复、可追溯、可验收的生产形态链路证明架构可扩展。

## 2. 目标与非目标

### 2.1 目标

完成以下闭环，并让每一步都能追溯、重放、审计：

```text
合成 CSV/HTTP 数据源
  → 字段映射与编码清洗
  → 采集批次与质量校验
  → 标准化事实
  → 版本化指标公式计算
  → 月度/年度结果
  → 红黄灯预警
  → 科室与脱敏明细下钻
  → PDCA 整改
  → 证据复核
  → 固定快照报告
```

第一条纵向切片至少覆盖四类指标：

1. 比例指标：i01，验证分子、分母、排除数和科室维度；
2. 单病种/重点质量指标：i03，验证指标明细和责任科室；
3. DRG/加权指标：i11，验证加权聚合而非简单平均；
4. 年末快照指标：i12，验证年末取值和年度完整性。

### 2.2 非目标

- 不在 v3 连接真实 HIS、EMR、LIS、PACS、HQMS、HRP 或国家平台；使用本地模拟服务器和合成适配器。
- 不在 v3 声称已覆盖完整 2025 版标准，不复制来源不清晰的商业指标清单。
- 不在 v3 启用自动写入式 AI。AI 如需预留，只能做检索、解释或待办草稿，写入必须人工确认、权限校验并回查。
- 不把本地测试通过写成真实生产上线、安全评估或真实医院验收通过。
- 不重写 v1 页面，不破坏 v1/v2 已有端点和契约。

## 3. 不可突破的约束

- 修改前必须阅读根目录 `AGENTS.md`、`交接文档.md`、本文件、v0.2 契约、两份参考 PDF 和与任务相关的正式 docs/policy；原始 `docs/01` 至 `05` 与政策文件只读。
- 共享接口必须先更新契约，再修改后端、前端和测试；不能静默改变 v1/v2 响应形状。
- `review.profile=prod` 必须拒绝 `X-Demo-Role`；未认证请求拒绝；医院是租户边界，科室是范围边界，所有列表、导出、批处理和异步任务都在服务端过滤。
- 已发布标准版本、已应用批次、指标结果快照、材料版本和审计事件不提供修改删除端点；更正使用新版本、新批次或冲正记录。
- 演示数据必须在 seed/demo/adapter 层；核心业务规则不得只依赖演示数组或固定样例。
- 迁移只追加；PostgreSQL 是生产形态主路径，H2 仅作为本地测试实现；核心业务不能依赖 H2 特有 SQL。
- 页面持续显示“演示环境 / 合成数据”；不提交 `target`、`node_modules`、`.runtime`、日志、数据库或真实数据。

## 4. 版本与架构决策

### 4.1 API 版本

- 保持 `/api` v1 和 `/api/v2` 现有契约稳定。
- 新能力优先以兼容方式扩展 v2；只要涉及指标定义、血缘、预警或结果形状的破坏性变化，使用 `/api/v3`。
- 新契约文件为 `docs/v3-api-contract.md`，先写契约和错误码，再写两端。

### 4.2 新增领域边界

v3 新代码放在 `backend/src/main/java/cn/demo/review/v3/`，复用稳定的 v2 认证、组织、审计和材料能力，不复制 v2 已有实现。

建议领域包：

- `v3/metric`：指标定义、公式版本、结果聚合；
- `v3/ingestion`：数据源、字段映射、采集批次、清洗和重放；
- `v3/lineage`：来源、批次、规则、结果、报告之间的血缘查询；
- `v3/alert`：阈值、趋势、跳变和质量告警；
- `v3/assessment`：预警/条款/抽查到整改项目的关联；
- `v3/web`：REST 控制器和错误映射。

前端新增 `frontend/src/v3/**`，只做 v3 工作台和数据链路视图；v1/v2 页面保持可用。

### 4.3 迁移与存储

- 当前 schema migration 版本为 3；v3 数据库变更使用版本 4 及以后。
- 新迁移建议：`backend/src/main/java/cn/demo/review/v2/platform/V4Schema.java` 和 `backend/src/main/resources/db/migration/postgresql/V4__v03_data_platform.sql`；若实现选择独立迁移器，必须在契约和交接记录中说明。
- 指标结果、批次、公式和审计元数据与文件内容分离；文件继续通过 `BlobStore` 接口访问，不能把真实路径暴露给前端。

## 5. 领域模型与最小接口

### 5.1 指标定义与公式

新增版本化指标定义，至少包含：

```text
metricCode, versionId, name, unit, direction, ownerScope,
formulaType, inputFields, filters, aggregation, target, warning,
sourceRequirements, evidenceRequirements, effectiveFrom, status
```

`formulaType` 只允许受控类型：

- `ratio`：分子 / 分母；
- `weighted_ratio`：Σ分子 / Σ分母；
- `month_avg`：月度事实平均；
- `year_end_snapshot`：年度末快照；
- `drg_formula`：按定义的年度加权输入计算；
- `trend`：连续周期趋势和滑坡检测。

禁止接受任意 SQL 或任意脚本作为公式。每次公式、阈值或输入字段变化都生成新版本。

### 5.2 数据接入与质量

最小对象：

```text
DataSource
SourceMapping
CollectionBatch
CanonicalFact
QualityIssue
CalculationTrace
LineageEdge
```

最小接口建议：

```text
GET  /api/v3/data-sources
POST /api/v3/data-sources/{id}/preview
GET  /api/v3/source-mappings?sourceCode=...
POST /api/v3/ingestion/batches
GET  /api/v3/ingestion/batches/{id}
POST /api/v3/ingestion/batches/{id}/apply
POST /api/v3/ingestion/batches/{id}/replay
GET  /api/v3/lineage/results/{resultId}
```

质量规则至少覆盖：未知字段、必填字段缺失、编码无法映射、单位不符、分子/分母关系错误、重复事实、期间重叠、科室无归属、异常跳变。错误批次不得进入指标结果或试算。

### 5.3 结果、预警与整改

最小接口建议：

```text
GET  /api/v3/metric-results?metricCode=...&period=...&deptCode=...
GET  /api/v3/metric-results/{id}/drilldown
GET  /api/v3/alerts
POST /api/v3/alerts/{id}/ack
POST /api/v3/alerts/{id}/assign
POST /api/v3/improvements/from-alert
GET  /api/v3/improvements/{id}/lineage
```

结果必须返回：指标定义版本、周期、数值、目标/预警线、质量状态、批次 ID、计算规则版本、执行时间和可见范围。

预警类型至少包括：低于目标、超过预警线、连续恶化、异常跳变、数据缺失、质量问题未处理。预警状态至少包括 `open → acknowledged → assigned → resolved/ignored`，状态变更必须审计。

## 7. v3 验收门槛

### 功能

- [ ] i01/i03/i11/i12 至少各有一条可追溯结果；i11 不允许按平均值退化。
- [ ] 一个故意错误的 CSV 能定位到行、字段和规则，且不会进入结果。
- [ ] 正确批次可重放；旧结果和旧报告保持不变。
- [ ] 指标结果可从医院下钻到科室和脱敏明细，再反查来源批次和公式版本。
- [ ] 告警可确认、分派、解决或忽略，并可直接创建整改项目。
- [ ] 整改项目可上传证据、复核效果、形成报告。

### 安全与边界

- [ ] prod profile 拒绝 `X-Demo-Role`，未认证请求返回 401。
- [ ] 跨医院、跨科室、跨角色读取和写入全部服务端拒绝。
- [ ] 导出、下载、下钻、批处理和异步任务均携带医院/科室范围。
- [ ] 患者级字段只在允许的脱敏明细范围出现；报告和领导视图不泄露。

### 工程

- [ ] 现有 v1/v2 测试和集成不回退。
- [ ] 后端新增公式、质量、血缘、告警、整改和权限测试。
- [ ] 前端新增工作台逻辑测试、类型检查和构建通过。
- [ ] `scripts/verify.ps1`、`node scripts/integration-check.mjs` 和 v3 专项集成检查通过。
- [ ] PostgreSQL 迁移、备份恢复、对象存储替身和认证替身均有实际命令结果。
- [ ] 未验证事项明确标注“未验证”，不写成生产通过。

## 8. 交付与交接格式

WorkBuddy 完成后必须在 `交接文档.md` 追加记录：

1. 完成功能、未完成功能和实际文件范围；
2. 契约变化、迁移版本、配置和回滚方式；
3. 实际执行命令及通过/失败/跳过/未运行数量；
4. 当前服务进程、端口、数据目录和复现步骤；
5. 真实接入前仍需用户提供的数据字典、接口样例、身份协议、组织架构、保留期限和部署条件；
6. 下一位 AI 的明确入口。

最终结论只能使用：

- “本地演示/合成数据范围已验证”；或
- “生产形态接口/替身已验证，真实接入未验证”。

不得使用“真实生产环境已验证”，除非用户明确提供真实环境并完成相应验收。
